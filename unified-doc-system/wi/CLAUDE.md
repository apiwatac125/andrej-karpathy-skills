## สิ่งที่โปรเจกต์นี้ทำ

Google Apps Script Web App ควบคุมเอกสารคุณภาพ (WI / SP / ED / LB) แทนการเดินแฟ้มเซ็นกระดาษ:
ผู้จัดทำอัปโหลดไฟล์เอกสาร + กรอกข้อมูลควบคุมเอกสาร + เซ็น → ระบบส่งอีเมลให้ผู้ทบทวนและผู้อนุมัติ
ลงนามต่อตามลำดับ → อนุมัติครบแล้วสร้าง "ใบปกควบคุมเอกสาร" เป็น PDF เก็บคู่กับไฟล์ใน Drive
และตีฉบับก่อนหน้าเป็น "ยกเลิกใช้" → ดูย้อนหลังได้ที่หน้าคลังเอกสาร

สร้างโดยยืมโครงจาก **`D:\SP Medtech project`** (SP-MT-07 Selection Web App) — pattern ที่ reuse มา:
token approval ใน URL, signature pad 2 ช่องทาง, HTML→PDF เก็บ Drive, คลังเอกสารหลายระดับ,
`runSetup()` แบบ idempotent, อ่าน/เขียนชีทตามชื่อคอลัมน์

v2.0 เพิ่มโมดูล **ตรวจติดตามภายใน (Internal Audit)** และ **CAPA** ต่อจากโมดูลเอกสารของ v1.0
ปิดวง: WI → Audit → Finding → CAPA → WI ฉบับใหม่

## สถานะปัจจุบัน

เขียนครบ end-to-end แล้ว **แต่ยังไม่ได้ deploy และยังไม่ได้ทดสอบบน Apps Script จริง**
(ตรวจแล้วแค่ syntax ของ `.gs` และ JS ใน HTML ทุกไฟล์ผ่าน `node --check` + เช็คว่าทุกฟังก์ชันที่
หน้าเว็บเรียกผ่าน `google.script.run` มีจริงฝั่ง server)

- `Sign.html` — หน้าลงนามเอกสาร (`?page=sign&id&token`) ใช้ทั้งขั้นทบทวนและขั้นอนุมัติ

- `Styles.html` / `SigPad.html` — partial include เข้าทุกหน้าผ่าน `include()`

- `preview.html` / `preview-v2.html` — mockup คลิกได้ ไม่พึ่ง backend (ยังไม่มี DAR / ค้นหา)
- `preview-archive-search.html` — **ไม่ใช่ mockup**: ประกอบจาก `Archive.html` + `Nav.html` +
  `Styles.html` ตัวจริง แล้ว stub แค่ `google.script.run` ใช้ดู UI จริงนอก Apps Script

## สถาปัตยกรรม / การตัดสินใจสำคัญ

1. **1 แถว = 1 ฉบับ** ในแท็บ `Documents` ไม่ใช่ 1 แถวต่อเอกสาร — ประวัติการแก้ไขจึงเป็น audit trail
   โดยธรรมชาติ ไม่ต้องมีแท็บ history แยก. ฉบับปัจจุบันของเลขเอกสาร = แถวที่ `status = อนุมัติแล้ว`

2. **`revision` ไม่ใช่เลขที่แสดงบนเอกสาร — เป็นแค่ลำดับภายในสำหรับเรียง** (0,1,2,…)
   เลขที่พิมพ์บนหัวเอกสารจริงคือ `edition` + `amendment` → `editionLabel_()` ได้ `"D"` หรือ `"D/1"`
   `revision` ยังคำนวณฝั่ง server เสมอ (ฉบับใหม่สุด +1) ส่วน `edition` **คนกรอกเป็นคนระบุ**
   เพราะเป็นตัวอักษรได้ (ดูข้อ 32)

3. **กันยื่นซ้อน**: ถ้า `doc_code` นั้นมีฉบับสถานะ `รอทบทวน`/`รออนุมัติ` อยู่ จะ throw ไม่ให้ส่งฉบับใหม่
   (ควบคุมเอกสารต้องไม่มี 2 ฉบับวิ่งในสายอนุมัติพร้อมกัน)

4. **อนุมัติ 3 ขั้น** — ผู้จัดทำเซ็นตอน upload (ไม่ใช่ขั้นรออนุมัติ), แล้ว **ผู้ทบทวน → ผู้อนุมัติ**
   token เดียวใช้ทั้ง 2 ขั้น แต่ `signDocument` ตัดสินขั้นจาก `status` เอง client ข้ามขั้นไม่ได้
   ถ้า `reviewer_email` ของงานนั้นว่าง จะข้ามขั้นทบทวนไปรอผู้อนุมัติเลย (เหมือน supervisor ใน SP-MT-07)

5. **ผู้ลงนามตั้งต่องาน**: แท็บ `Units` เก็บ `reviewer_email`/`approver_email` ต่อ 1 งาน
   เว้นว่าง = ใช้ค่ากลางใน `Config` (`resolveSigners_()`) — ต่างจาก SP-MT-07 ที่มีผู้อนุมัติชุดเดียว

6. **e-signature** เหมือน SP-MT-07: วาดบน canvas 400x150 หรือแนบรูป (PNG/JPG ≤5MB ย่อลงกรอบอัตโนมัติ)
   เก็บเป็น data URL ในเซลล์ — server `validateSignature_()` ตรวจ prefix `data:image/(png|jpeg);base64,`
   + ความยาว < 50,000 (เพดานต่อเซลล์ของ Sheets) / client fallback JPEG q0.85 ถ้า PNG ≥45k
   / canvas พื้นขาวเสมอกัน JPEG ออกมาดำ
   โค้ดกล่องเซ็นอยู่ที่ `SigPad.html` ตัวเดียว (`WiSig.mount(containerId)`) ใช้ร่วมทั้ง 2 หน้า

7. **ไฟล์แนบส่งเป็น base64**: `google.script.run` ส่ง `File` object ไม่ได้ หน้าเว็บจึง `readAsDataURL`
   แล้วตัดเอาเฉพาะส่วนหลัง comma ส่งเป็น `file.dataBase64` — server ตรวจ `ALLOWED_MIME` ซ้ำอีกชั้น
   (ตรวจฝั่ง client เดียวไม่ได้ เพราะ payload แก้ได้) เพดาน `MAX_FILE_MB = 10`

8. **แชร์ไฟล์เป็นรายคน** (`addViewer`) ตามขั้น: ผู้ทบทวนตอน submit → ผู้อนุมัติตอนผ่านทบทวน →
   ผู้จัดทำตอนอนุมัติครบ. ไม่เปิด link sharing ทั้งโดเมน. ทุก `addViewer` หุ้ม try/catch
   เพราะอีเมลนอกองค์กรอาจแชร์ไม่ได้ และไม่ควรทำให้ flow ทั้งหมดล้ม

9. **ใบปก PDF** สร้างตอน `status → อนุมัติแล้ว` ด้วย `Utilities.newBlob(html, HTML).getAs(PDF)`
   (HTML จาก `buildCoverHtml_()`) เก็บใน `ราก/งาน/ประเภทเอกสาร` — **หุ้ม try/catch** ห้าม PDF พัง
   ทำให้การอนุมัติล้ม → สร้างย้อนหลังได้ด้วย `regenerateCoverPdf(docId)` (ปุ่มในหน้าคลัง)
   **DriveApp = scope ใหม่ ต้อง re-authorize + Deploy New version ก่อนใบปกจึงจะสร้างได้**

10. **วันที่ประกาศใช้** (คำที่เอกสารจริงใช้ ไม่ใช่ "วันที่มีผลบังคับใช้") ถ้าผู้จัดทำไม่ระบุ ใช้วันที่อนุมัติ — แล้วคำนวณ `next_review_date`
    จาก `review_cycle_months` (ค่าตั้งต้น 24 เดือน) → `getDueForReview(days)` ใช้เตือนก่อน ISO audit
    (หน้าคลังแสดงกล่องเตือน 90 วัน)

11. **ลิงก์ข้ามหน้าต้องใช้ URL เต็มเสมอ** (บทเรียนจาก SP-MT-07): HtmlService เสิร์ฟในกรอบ iframe บน
    `googleusercontent.com` — `href="?page=archive"` หรือ `href="#..."` resolve เทียบโดเมน sandbox
    ไม่เข้า `doGet` จึงต้อง render ทุกหน้าผ่าน `createTemplateFromFile` + ฝัง
    `tpl.baseUrl = ScriptApp.getService().getUrl()` แล้วอ่านผ่าน `<body data-base>` ใน JS
    / ด้วยเหตุผลเดียวกัน หน้าคลังสลับมุมมองด้วย JS state (`selectedUnit`/`selectedType`) **ห้ามใช้ URL hash**

12. **`access: "ANYONE"` ใน manifest** (เหมือน SP-MT-07 ที่ผู้ใช้เป็น Gmail ส่วนตัว ไม่ได้อยู่ใน
    Workspace domain) → `Session.getActiveUser().getEmail()` คืนค่าว่าง จึงมีช่อง "อีเมลผู้จัดทำ"
    ให้กรอกเอง และ `submitDocument` ใช้ค่าจากฟอร์มเป็นตัวสำรอง. ถ้าย้ายไป Workspace จริงให้เปลี่ยน
    เป็น `"DOMAIN"` (ปลอดภัยกว่า + เติมอีเมลอัตโนมัติ)

13. **หน้าคลัง cache 5 นาที** ที่ `CacheService` key `wi_archive_v1` ล้างทุกครั้งที่ submit/sign
    (`clearArchiveCache_()`) — payload ไม่ใส่ field ลายเซ็น เพราะ data URL จะทำให้ทะลุเพดาน cache
    และเปลืองแบนด์วิดท์ (หน้าคลังไม่ต้องแสดงลายเซ็น)

14. **แถวที่ไม่มี `unit` หรือ `doc_code` ไม่ขึ้นในคลัง** (ข้ามไป) — กันแถวที่แก้มือในชีทแล้วข้อมูลไม่ครบ
    มาทำให้หน้าคลังพัง

## การตัดสินใจของ v2.0 (Audit + CAPA)

15. **แยกไฟล์ `AuditCapa.gs`** ไม่ยัดลง Code.gs — GAS มองทุก `.gs` เป็น global scope เดียวกัน
    จึงเรียก helper ของกันและกันได้ตรง ๆ (`getSheet_`, `validateSignature_`, `getDriveRoot_` ฯลฯ)
    แยกไฟล์เพื่อให้แก้โมดูลเอกสารกับโมดูลตรวจติดตามคนละเรื่องได้โดยไม่ชนกัน

16. **Finding เป็นแถวแยก ไม่ใช่ JSON ก้อนเดียวในแถว audit** — เพราะ finding ต้องผูก 1:1 กับ CAPA
    และต้อง query ข้ามรอบตรวจได้ (เช่น "ข้อกำหนด 7.3 ถูกตรวจพบซ้ำกี่รอบ")

17. **NC ทุกข้อต้องมี CAPA ก่อนปิดรอบตรวจ** — `submitAuditSummary()` throw ถ้ายังมี NC ที่ `capa_id`
    ว่าง เป็นกติกาที่ระบบบังคับ ไม่ใช่แค่ความเคยชินของคนใช้ (`FINDING_GRADES[].needsCapa` คุมว่าระดับไหนบังคับ)

18. **CAPA ข้ามขั้นไม่ได้**: `reportCapaAction()` throw ถ้า `root_cause` ยังว่าง — กันพฤติกรรมที่พบบ่อยคือ
    เขียนแต่การแก้เฉพาะหน้า (correction) แล้วปิดเรื่อง ซึ่งไม่ใช่ corrective action
    / `verifyCapa()` ถ้า **ไม่ผ่าน** จะตีกลับเป็น `กำลังแก้ไข` พร้อมกำหนดใหม่ ไม่ปิด CAPA

19. **ปิด CAPA แล้วปิด finding ต้นทางให้อัตโนมัติ** (`FINDING_STATUS.CLOSED`) — สถานะเดียวที่คนกรอก
    ไม่ต้องมาซิงค์เอง / ยกเลิก CAPA จะคืน finding กลับเป็น `เปิด` และล้าง `capa_id`

20. **`linkCapaToDocument()` ผูก CAPA กับเลขเอกสาร** แล้วหาฉบับล่าสุดของเลขนั้นให้เอง — เป็นเส้นที่ทำให้
    ตอน audit ไล่ย้อนได้ว่า WI Rev. นี้ออกมาเพราะ CAPA ข้อไหน (ข้อกำหนด 8.7 ต้องการ traceability นี้)

21. **เลขที่เอกสารเป็น serial ต่อปี พ.ศ.** (`nextSerial_`): `IA-2569-01`, `CAPA-2569-003`,
    finding เป็น `<เลขรอบ>/F01` — คำนวณจากแถวที่มีอยู่ ไม่เก็บ counter แยก (กัน counter เพี้ยนเวลาลบแถว)

22. **สิทธิ์ตามหน้าที่ทำไว้แต่ "บังคับไม่ได้" ถ้า deploy แบบ ANYONE** — `getCurrentUser()` คืน
    `known:false` และหน้ารวมขึ้นแถบเตือนตรง ๆ ไม่แกล้งทำเป็นว่ามีการคุมสิทธิ์
    `requireRole_()` จะ throw ก็ต่อเมื่อ `Config.enforce_roles = TRUE` **และ** รู้ตัวตนผู้ใช้
    (ตั้งใจให้ fail-open เพราะ fail-closed บน ANYONE = ใช้งานไม่ได้เลย)

23. **`readTable_()` / `findRowById_()` / `appendByName_()` เป็น helper กลางของโมดูลใหม่** —
    อ่าน/เขียนตามชื่อคอลัมน์เหมือนโมดูลเอกสาร เพิ่มคอลัมน์ต่อท้ายได้โดยไม่ต้องแก้โค้ดอ่าน

24. **หน้ารวมเป็นหน้าแรกแทนหน้าส่งเอกสาร** — หน้าส่งเอกสารย้ายไป `?page=upload`
    และเมนูทุกหน้ารวมไว้ที่ `Nav.html` ตัวเดียว (อ่าน `<body data-base>` / `<body data-page>`)

## การตัดสินใจของ v2.1 (DAR)

25. **DAR เป็น "ประตูหน้า" ของโมดูลเอกสาร ไม่ใช่โมดูลคู่ขนาน** — เอกสารที่ออกตามคำขอผูกกลับด้วย
    คอลัมน์ `dar_id` ใน `Documents` และ DAR ปิดเองใน `signDocument()` ตอนอนุมัติครบ
    (`closeDarForDocument_` หุ้ม try/catch — DAR ที่ปิดไม่สำเร็จห้ามทำให้การอนุมัติเอกสารล้ม)

26. **`require_dar` ตั้งต้นเป็น FALSE** — ระบบที่บังคับ DAR ตั้งแต่วันแรกจะทำให้ของเดิมส่งไม่ได้ทันที
    ตั้งให้ opt-in เพื่อให้ทยอยปรับตัว · `validateDarForSubmit_()` เป็นจุดเดียวที่ตัดสินเรื่องนี้

27. **คำขอประเภท "ยกเลิก" มีผลทันทีตอนอนุมัติ ไม่ต้องรออัปโหลด** — เพราะไม่มีไฟล์จะอัปโหลด
    นี่คือทางเดียวที่ปลดเอกสารเป็น `ยกเลิกใช้` ได้โดยไม่มีฉบับใหม่มาแทน (ก่อน v2.1 ทำไม่ได้เลย
    ทั้งที่ ISO 15189 ข้อ 8.3 ต้องการให้ควบคุมเอกสารยกเลิก)

28. **ผู้อนุมัติคำขอเลือกเองตามสิ่งที่มี** — `darApprover_()` ใช้ `qm_email` ถ้ามี (v2.x)
    ไม่มีก็ตกมาที่ `approver_email` ของงานนั้น (v1.x) — ทำให้ `DocRequest.gs` ไฟล์เดียวใช้ได้ทั้ง 2 สาย
    เช่นเดียวกับ `darRequireApprover_()` ที่เรียก `requireRole_` ก็ต่อเมื่อ `typeof` เป็น function

29. **ตัวเลือกแหล่งที่มา "CAPA" โผล่เฉพาะเมื่อมีโมดูล CAPA** — `darSources_()` เช็ค `SHEET_NAMES.CAPAS`
    ซึ่ง undefined ใน v1.x · หลักเดียวกันนี้ทำให้ `Dar.html` ไฟล์เดียวใช้ได้ทั้ง 2 สาย
    (`getCapaForDar` ถูกเรียกเฉพาะเมื่อมี `?capa=` ซึ่ง router ของ v1.x ไม่เคยส่งมา)

30. **ประเมินผลกระทบเป็นช่องบังคับคิด ไม่ใช่ช่องบังคับกรอก** — 3 ข้อ (อบรม / กระทบผลที่รายงานไปแล้ว /
    เอกสารที่ต้องแก้ตาม) เก็บเป็นคอลัมน์แยกเพื่อ query ได้ · ถ้าติ๊ก "กระทบผลที่รายงานไปแล้ว"
    หน้าพิจารณาจะขึ้นแถบเตือนเรื่องข้อ 7.5 (ต้องพิจารณาเรียกคืน/แก้ไขรายงานผล)

31. **`Common.gs` เกิดจาก v2.1** — helper ที่เคยอยู่ใน `AuditCapa.gs` ถูกย้ายออกมาเพราะ `DocRequest.gs`
    ต้องใช้ แต่ v1.1 ไม่มี `AuditCapa.gs` · กฎของไฟล์นี้: **ห้ามอ้างถึงแท็บหรือค่าคงที่ของโมดูลใดโมดูลหนึ่ง**
    (ยกเว้น `SHEET_NAMES.CONFIG` ที่มีทุกสาย)

## การตัดสินใจของ v2.2 — แก้ให้ตรงเอกสารจริง + ค้นหาเนื้อหา

> อ้างอิงไฟล์จริง `WI-MB-08` / `WI-MB-07` ที่ผู้ใช้ส่งมา (แปลงด้วย `antiword` บนเครื่อง ไม่ใช่บน GAS)

32. **ฉบับที่เป็นตัวอักษรได้ ระบบจึงไม่บวกเลขอัตโนมัติ** — ของจริงเดิน `1 → 2 → C → D → D/1`
    (กระโดดจาก `2` ไป `C` ตอนเปลี่ยนระบบเลขเอกสาร) ถ้าบังคับสูตรจะพัง
    `nextEdition_()` จึงแค่**เดาค่าตั้งต้น** (ตัวเลข +1, ตัวอักษรเลื่อนตัวถัดไป) แล้วให้แก้ทับได้เสมอ
    — server กันฉบับซ้ำ `(edition, amendment)` ให้แทน

33. **3 ตัวนับแยกกันตามตารางบันทึกประวัติในเอกสารจริง**: `edition` (ฉบับที่) / `amendment` (แก้ไขครั้งที่)
    / `review_count` (ทบทวนครั้งที่) + `change_kind` 4 แบบ · แบบ `review` = "ทบทวนเอกสาร (ไม่มีแก้ไข)"
    ซึ่ง**ฉบับที่ไม่เปลี่ยนแต่ต้องเซ็นใหม่** และเป็นกรณีเดียวที่ยอมให้ `(edition, amendment)` ซ้ำได้

34. **`DOC_TYPES` ใช้รหัสจริงของกลุ่มงาน**: `WI` / `SP` / `ED` / `LB` (+ `FM` / `QM` เผื่อไว้)
    ไม่ใช่ WI/SOP/FM/QM ที่เดาไว้ตอนแรก · รหัสลูกผูกกับพ่อด้วยชื่อ (`ED-WIMB08-01` = ED ของ WI-MB-08)
    แต่**ยังไม่ได้ทำ parent-child ในระบบ** — เป็นแค่ข้อตกลงการตั้งชื่อ

35. **`control_type` + `copy_no`** มาจากช่อง "เอกสารฉบับนี้เป็น: ☑ เอกสารควบคุม สำเนาฉบับที่ __"
    บนหัวเอกสารจริง · พิมพ์ลงใบปกควบคุมเอกสาร

36. **ค้นหาเนื้อหาไม่ใช้ LLM โดยเจตนา** (ผู้ใช้เลือกเอง: อยากให้อยู่ใน sandbox)
    `DocSearch.gs` ดึงข้อความจากไฟล์ด้วย `Drive.Files.create` (Advanced Drive Service v3)
    → Google Doc ชั่วคราว → `getBody().getText()` → ลบทิ้ง · PDF สแกนถูก OCR ให้เอง (`ocrLanguage: 'th'`)
    เก็บลงแท็บ `DocText` chunk ละ 45,000 ตัวอักษร (เพดานเซลล์ Sheets คือ 50,000)
    **ทำครั้งเดียวตอนอนุมัติ** ไม่ใช่ทุกครั้งที่ค้น — หุ้ม try/catch index พังห้ามทำให้อนุมัติล้ม

37. **ค้นแล้วคืนข้อความจริงจากเอกสาร ไม่เรียบเรียงใหม่** — `searchArchive()` คืน snippet ±110 ตัวอักษร
    รอบคำที่เจอ · คำที่อยู่ติดกัน (เช่น "colony count") จะตัดทับกัน จึงข้าม snippet ที่ห่างกัน <200 ตัวอักษร

38. **ค้นเฉพาะฉบับ "อนุมัติแล้ว" เป็นค่าตั้งต้น** — ถ้าปล่อยให้ฉบับยกเลิกใช้โผล่มาปน คนจะหยิบ
    วิธีปฏิบัติเก่าไปใช้ ซึ่งผิด ISO 15189 ข้อ 8.3 ตรง ๆ · มี checkbox ให้รวมได้เมื่อจงใจ

39. **UI ค้นหาเป็น widget ลอยมุมขวาล่าง ไม่ใช่ช่องค้นบนหน้าคลัง** — วางใน `Nav.html` จึงติดไปทุกหน้า
    โดยไม่ต้องแก้ทุก template · ช่องค้นเดิมที่หัวหน้าคลังถูกถอดออกแล้ว หน้าคลังเหลือแค่โหมดเรียกดู

40. **`appsscript.json` ประกาศ Advanced Drive Service v3** — ตอนติดตั้งต้องเปิด Drive API
    ใน Apps Script → Services แล้ว **re-authorize** เพราะเป็น scope ใหม่ ไม่งั้น `extractText_` พัง
    (แต่การอนุมัติเอกสารยังทำงานปกติ)

## สิ่งที่ยังไม่ได้ทำ (ถ้าจะต่อ)

- **ยังไม่เคยรัน `DocSearch.gs` บน Apps Script จริงเลย** — ไม่ยืนยันว่า Drive v3 แปลง `.doc` เก่า
  (OLE2) ได้ · ถ้าไม่ได้ ต้องให้คนอัปโหลดเป็น PDF/docx แทน
- เอกสารใหญ่มาก (หลายร้อยหน้า) อาจชนเพดานรัน 6 นาทีตอน index → ลด `limit` ของ `reindexArchive`
- `preview.html` / `preview-v2.html` ยังไม่มีหน้า DAR และ widget ค้นหาในตัวสาธิต
- แจ้งเตือนอัตโนมัติ: ใกล้กำหนดทบทวนเอกสาร / CAPA ใกล้ครบกำหนด — มีข้อมูลพร้อมแล้วที่
  `getDueForReview()` และ `getHomeData().capas.overdueList` ขาดแค่ time-driven trigger ส่งอีเมล
- แผนการตรวจประจำปี (audit programme) — ตอนนี้เปิดรอบตรวจทีละรอบ ยังไม่มีมุมมองทั้งปี
- ทะเบียนเอกสารแบบพิมพ์ได้ (Master List of Documents) — คล้าย `Avl.html` ของ SP-MT-07
- แจกจ่าย/รับทราบเอกสาร (acknowledge ว่าอ่าน WI ฉบับใหม่แล้ว)
- parent-child ของรหัสลูก (`ED-WIMB08-01` ↔ `WI-MB-08`) และ template generator โครง WI 8 หัวข้อ
- บันทึกระยะเก็บรักษาหลังยกเลิก 1 ปี ตอนอนุมัติ DAR ประเภทยกเลิก
- rate limit ของ `searchArchive` — ตอนนี้ deploy แบบ ANYONE ใครมีลิงก์ก็ยิงค้นได้
- การทบทวนการบริหาร (management review) ที่ดึงตัวเลขจาก audit/CAPA มาสรุปอัตโนมัติ
