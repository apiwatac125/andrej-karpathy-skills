# WI Document Control v2.1 — เอกสารคุณภาพ + DAR + ตรวจติดตามภายใน + CAPA

Google Apps Script Web App สำหรับระบบคุณภาพห้องปฏิบัติการตาม ISO 15189
โครงเดียวกับ **SP-MT-07 Selection Web App** ต่างกันที่ตัวเอกสารเป็น **ไฟล์ที่อัปโหลด** ไม่ใช่ฟอร์มที่กรอกในเว็บ

> เวอร์ชันก่อนหน้า (เอกสารอย่างเดียว) เก็บไว้ที่ `../wi-doc-control-v1.0` — ดู `VERSION.md`

## ติดตั้ง

1. สร้างโปรเจกต์ใหม่ที่ [script.google.com](https://script.google.com) → ตั้งชื่อ `WI Document Control`
2. คัดลอกไฟล์เข้าโปรเจกต์ (หรือ `clasp push` ถ้าตั้ง `.clasp.json` แล้ว):
   - `Code.gs` (โมดูลเอกสาร) / `Common.gs` (helper กลาง) / `DocRequest.gs` (DAR) / `AuditCapa.gs` (Audit + CAPA)
   - `Home.html` / `Dar.html` / `Upload.html` / `Sign.html` / `Archive.html` / `Audit.html` / `Capa.html`
   - `Nav.html` / `Styles.html` / `SigPad.html` (partial ที่ include เข้าทุกหน้า)
   - `appsscript.json` (เปิด Project Settings → ติ๊ก "Show appsscript.json manifest file" ก่อน)
3. เมนู **Run → runSetup** หนึ่งครั้ง → อนุญาตสิทธิ์ → ดูลิงก์ Spreadsheet ใน Log
4. เปิด Spreadsheet ที่ได้ แล้วตั้งค่า:
   - แท็บ **Units** — รายชื่องาน + `reviewer_email` / `approver_email` ต่องาน (เว้นว่าง = ใช้ค่ากลางใน Config)
   - แท็บ **Config** — `reviewer_email` / `approver_email` ค่ากลาง, `qm_email` (ผู้จัดการคุณภาพ —
     คนลงนามปิดรอบตรวจและทวนสอบ CAPA), `org_line` (ชื่อหน่วยงานบนหัวเอกสาร),
     `default_review_cycle_months`, `capa_default_due_days`, `effectiveness_check_days`
   - แท็บ **People** (ถ้าจะคุมสิทธิ์) — `email` / `name` / `role` / `unit` · role ที่ใช้ได้:
     `staff` `head` `qm` `auditor` `admin`
5. **Deploy → New deployment → Web app**
   - Execute as: **Me**
   - Who has access: **Anyone** (ดูหัวข้อ "สิทธิ์การเข้าถึง" ด้านล่าง)
6. เปิด URL ที่ได้ → ส่งเอกสารทดสอบ 1 ฉบับ

> `runSetup()` รันซ้ำได้ ใช้ migrate ชีทเก่าให้มีคอลัมน์/คีย์ Config ครบเมื่ออัปเดตโค้ด

## สิทธิ์การเข้าถึง

ค่าตั้งต้น `appsscript.json` ใช้ `access: "ANYONE"` เหมือน SP-MT-07 เพราะผู้ใช้เป็นบัญชี Gmail ส่วนตัว
ไม่ได้อยู่ใน Google Workspace domain เดียวกัน ผลคือ:

- `Session.getActiveUser().getEmail()` คืนค่าว่าง → หน้าส่งเอกสารจึงมีช่อง **อีเมลผู้จัดทำ** ให้กรอกเอง
- การลงนามคุมด้วย **token ใน URL** (UUID ต่อเอกสาร) ไม่ได้คุมด้วย login
- ใครมีลิงก์ web app ก็ส่งเอกสารเข้าระบบได้ — ยอมรับได้เพราะทุกฉบับต้องผ่านการลงนาม 2 ขั้นก่อนบังคับใช้

ถ้าองค์กรใช้ Google Workspace จริง เปลี่ยน `access` เป็น `"DOMAIN"` จะได้ความปลอดภัยสูงกว่า
(อีเมลผู้จัดทำจะถูกเติมอัตโนมัติ และคนนอกองค์กรเปิดไม่ได้)

### สิทธิ์ตามหน้าที่ (v2.0)

ทะเบียนสิทธิ์อยู่ที่แท็บ **People** แต่ระบบ **บังคับสิทธิ์ไม่ได้ถ้า deploy แบบ ANYONE**
(ไม่รู้ว่าใครเป็นผู้ใช้) หน้ารวมจะขึ้นแถบเตือนให้เห็นชัดว่าเปิดกว้างอยู่

เปิดการบังคับสิทธิ์: `appsscript.json` → `access: "DOMAIN"` + ลงทะเบียนคนในแท็บ People +
ตั้ง `Config.enforce_roles = TRUE` จากนั้น action ที่สงวนไว้ (ลงนามปิดรอบตรวจ / ทวนสอบปิด CAPA /
ยกเลิก CAPA) จะจำกัดเฉพาะ role `qm` หรือ `admin`

## โครงข้อมูล

**Spreadsheet** (id เก็บใน Script Properties คีย์ `SHEET_ID`)

- `Documents` — 1 แถว = 1 ฉบับ (1 revision) ของเอกสาร โค้ดอ่าน/เขียนตาม **ชื่อคอลัมน์** ลำดับไม่สำคัญ
- `Units` — `unit`, `reviewer_email`, `reviewer_title`, `approver_email`, `approver_title`
- `Config` — คู่ `key` / `value`
- `DocRequests` — 1 แถว = 1 ใบขออนุมัติ (เลขที่ `DAR-<ปีพ.ศ.>-NNN`) ผูกกับ `capa_id` และเอกสารที่ออกตามคำขอ
- `Audits` — 1 แถว = 1 รอบตรวจ (เลขที่ `IA-<ปีพ.ศ.>-NN`)
- `Findings` — 1 แถว = 1 สิ่งที่ตรวจพบ (เลขที่ `IA-2569-01/F01`) ผูกกับ `audit_id` และ `capa_id`
- `CAPAs` — 1 แถว = 1 CAPA (เลขที่ `CAPA-<ปีพ.ศ.>-NNN`) ผูกกับ `finding_id` และ `related_doc_code`
- `People` — ทะเบียนสิทธิ์ `email` / `name` / `role` / `unit`

## สถานะเอกสาร

| สถานะ | ความหมาย |
|---|---|
| `รอทบทวน` | ผู้จัดทำส่งแล้ว รอผู้ทบทวนลงนาม |
| `รออนุมัติ` | ผ่านการทบทวนแล้ว รอผู้อนุมัติลงนาม |
| `อนุมัติแล้ว` | บังคับใช้ — มีใบปก PDF + วันที่มีผลบังคับใช้ + กำหนดทบทวนครั้งถัดไป |
| `ไม่ผ่านการทบทวน` / `ไม่อนุมัติ` | ตีกลับ ผู้จัดทำแก้แล้วส่งใหม่เป็น revision ถัดไป |
| `ยกเลิกใช้` | ถูกแทนด้วยฉบับใหม่ที่อนุมัติแล้ว (ระบบตีให้อัตโนมัติ) |

หนึ่งเลขเอกสารมีฉบับ `อนุมัติแล้ว` ได้ครั้งละ **1 ฉบับ** และห้ามมีฉบับที่ยังรอลงนามซ้อนกัน 2 ฉบับ

## สถานะใบขออนุมัติ (DAR, v2.1)

`รออนุมัติคำขอ` → `อนุมัติให้ดำเนินการ` → `ดำเนินการแล้ว` (หรือ `ไม่อนุมัติคำขอ` / `ยกเลิกคำขอ`)

- คำขอประเภท **ยกเลิกเอกสาร** ข้ามขั้น "อนุมัติให้ดำเนินการ" — อนุมัติแล้วตีเอกสารเป็น `ยกเลิกใช้` และปิดคำขอทันที
- คำขอประเภทจัดทำ/แก้ไข ปิดเองเมื่อเอกสารที่ออกตามคำขอได้รับอนุมัติครบ 3 ขั้น
- เลขเอกสารเดียวกันมีคำขอค้างได้ครั้งละ 1 ใบ
- `Config.require_dar = TRUE` เมื่อไรก็ตาม ส่งเอกสารเข้าระบบโดยไม่มี DAR ที่อนุมัติแล้วจะถูกปฏิเสธ

## สถานะรอบตรวจ / CAPA (v2.0)

**รอบตรวจ:** `วางแผน` → `กำลังตรวจ` (พอบันทึก finding ข้อแรก) → `รอลงนามสรุปผล` → `ปิดรอบ`
ปิดรอบไม่ได้ถ้ายังมี NC ที่ไม่ได้เปิด CAPA · ลงนาม 2 คน: หัวหน้าทีมผู้ตรวจ แล้ว QM

**ระดับสิ่งที่ตรวจพบ** — `NC ร้ายแรง` (ต้องมี CAPA, กำหนด 30 วัน) · `NC ไม่ร้ายแรง` (ต้องมี CAPA, 60 วัน) ·
`OFI` (ไม่บังคับ) · `เป็นไปตามข้อกำหนด`

**CAPA:** `เปิด (รอวิเคราะห์สาเหตุ)` → `กำลังแก้ไข` → `รอทวนสอบประสิทธิผล` → `ปิด` (หรือ `ยกเลิก`)
ระบบไม่ยอมให้ข้ามไปรายงานผลถ้ายังไม่กรอกสาเหตุราก และ **ทวนสอบ "ไม่ผ่าน" จะตีกลับไปขั้นแก้ไข ไม่ปิด**

## ข้อจำกัดที่ควรรู้

- **ขนาดไฟล์** เพดาน 10 MB (`MAX_FILE_MB` ใน `Code.gs`) — ไฟล์ถูกส่งเป็น base64 ผ่าน `google.script.run`
- **ลายเซ็น** เก็บเป็น data URL ในเซลล์ชีท เพดาน 50,000 ตัวอักษร/เซลล์ (PNG เกิน 45k จะ fallback เป็น JPEG q0.85)
- **อีเมล** MailApp โควตา 100 ฉบับ/วัน สำหรับบัญชี Gmail ทั่วไป
- **DriveApp = scope ใหม่** ถ้าเพิ่งเพิ่มโค้ดส่วน Drive ต้อง re-authorize + Deploy **New version** ก่อน
  ไม่งั้นใบปก PDF จะสร้างไม่ได้ (การอนุมัติยังสำเร็จ เพราะหุ้ม try/catch ไว้ — สร้างย้อนหลังได้จากหน้าคลัง)
- **ลิงก์ข้ามหน้าต้องใช้ URL เต็ม** HtmlService เสิร์ฟในกรอบ iframe บน `googleusercontent.com`
  `href="?page=archive"` จะวิ่งผิดโดเมน จึงฝัง `baseUrl` ผ่าน `<body data-base>` ทุกหน้า
